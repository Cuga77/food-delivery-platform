# Изменение API (contract-first)

Единственный источник правды — `api/openapi.yaml`. Код в `internal/gen/`
**генерируется** и руками не редактируется: правки будут стёрты следующим
`make gen`, а CI (`make gen-check`) не даст смерджить расхождение.

## Порядок работы

### 1. Правка контракта

`api/openapi.yaml`. Что важно соблюсти:

- **Деньги** — только `type: integer, format: int64` в копейках. Дробных типов
  в контракте нет нигде.
- **Новый код ошибки** добавляется в перечисление `ErrorCode` **и** в
  `internal/domain/errors.go` **и** в карту `statusByCode` в
  `internal/platform/problem/problem.go`. Разошлись — клиент получит 500 вместо
  осмысленного ответа.
- **Ошибочные ответы** описываются схемой `Problem`
  (`application/problem+json`), а не самодельным объектом.
- **Публичные эндпоинты** помечаются `security: []` — глобально включена
  аутентификация партнёра.
- Обязательные поля перечисляются в `required`, иначе генератор сделает
  указатель, и маппер придётся усложнять.

### 2. Генерация

```bash
make gen
```

Порождает `internal/gen/api.gen.go`: модели, `ServerInterface`,
`StrictServerInterface` и роутер chi.

### 3. Реализация метода

Компилятор сам укажет, чего не хватает: `Server` обязан удовлетворять
`gen.StrictServerInterface` (проверка `var _ gen.StrictServerInterface =
(*Server)(nil)` в `internal/adapters/http/router.go`).

Метод кладётся в один из трёх обработчиков:

| Файл | Что обслуживает |
|---|---|
| `internal/adapters/http/client_handler.go` | B2C: каталог, меню, заказы |
| `internal/adapters/http/partner_handler.go` | B2B: всё под `/api/v1/partner/` |
| `internal/adapters/http/health_handler.go` | `/health`, `/readyz` |

**Веб-клиент — отдельный транспорт.** Страницы в `internal/adapters/web` не
ходят в JSON API: они вызывают те же use cases напрямую. Новая возможность,
которую должен показывать веб-клиент, добавляется в `internal/app`, а потом
подключается к обоим транспортам независимо. Менять контракт ради страницы не
нужно.

Хендлер обязан оставаться тонким: разобрать вход → вызвать use case → отдать
результат. **Бизнес-правил в нём нет** — они живут в `internal/app` и
`internal/domain`.

Ошибки возвращаются как есть:

```go
order, err := h.orders.Create(ctx, toDomainDraft(*request.Body))
if err != nil {
    return nil, err // перевод в RFC 7807 делает ResponseErrorHandlerFunc
}
```

Никаких `http.Error`, статусов и ручной сборки тела ошибки в хендлерах.

### 4. Маппинг

`internal/adapters/http/mappers.go` — перевод между доменом и
сгенерированными моделями. Домен и контракт намеренно не совпадают.

Правила:

- пустые слайсы, а не `nil`: обязательное поле-массив должно сериализоваться в
  `[]`, а не в `null`;
- обход больших структур — по индексу (`for i := range xs`), иначе
  `gocritic` справедливо ругается на копирование;
- необязательное поле с значением по умолчанию (`available`, `description`)
  разворачивается в мапперe, а не в use case.

### 5. Прослойка, если эндпоинт особенный

Генератор умеет добавлять middleware только глобально, поэтому область действия
задаётся предикатом в `internal/adapters/http/router.go`:

```go
r.Use(scoped(isPartnerRequest, middleware.PartnerAuth(...)))
r.Use(scoped(isCreateOrderRequest, middleware.Idempotency(...)))
```

Новый партнёрский эндпоинт под `/api/v1/partner/` подхватывает аутентификацию
автоматически. Новая небезопасная операция, которую нельзя выполнять дважды,
требует добавления предиката для `Idempotency`.

### 6. Проверка

```bash
make gen-check   # сгенерированное совпадает с контрактом
make lint
make test
make up && make smoke
```

## Чего не делать

- Не редактировать `internal/gen/**`.
- Не принимать цены и суммы из тела запроса — сервер считает их сам по данным
  БД. Иначе клиент назначит свою цену.
- Не брать `restaurant_id` для партнёрских операций из тела или пути: только из
  контекста, куда его положила `PartnerAuth`.
- Не добавлять `omitempty` к полю, объявленному `required` в контракте.
