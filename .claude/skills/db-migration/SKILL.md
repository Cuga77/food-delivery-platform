# Изменение схемы БД

Схему меняют только миграции. Приложение её не создаёт и не «доводит» на старте:
`migrate` — отдельный контейнер, отрабатывающий до запуска `api`.

## 1. Создать пару файлов

```bash
make migrate-new name=add_promo_codes
```

Появятся `migrations/000003_add_promo_codes.up.sql` и `.down.sql`.
**Down-миграция обязательна и обязана работать** — это проверяет
интеграционный тест `TestMigrations_AreReversible`, который прогоняет
`down` до нуля и `up` обратно.

## 2. Написать SQL

Соглашения схемы, которых стоит держаться:

| Что | Как принято здесь |
|---|---|
| Первичный ключ | `BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` |
| Деньги | `BIGINT` в копейках + `CHECK (... >= 0)`, никогда не `NUMERIC`/`FLOAT` |
| Время | `TIMESTAMPTZ NOT NULL DEFAULT NOW()` |
| Перечисления | `VARCHAR(32)` + `CHECK (col IN (...))`, а не тип `ENUM` |
| Опциональность | явный `NULL` со смыслом в `COMMENT ON COLUMN` |

Инварианты дублируются в схеме, даже если проверяются в коде: `CHECK
(line_total_kopecks = unit_price_kopecks * qty)` не даст ошибке в приложении
испортить данные.

Оборачивайте миграцию в `BEGIN; ... COMMIT;`, кроме случаев, где это
невозможно (`CREATE INDEX CONCURRENTLY`).

Индекс добавляется под конкретный запрос, а не «на всякий случай». Если запрос
выбирает подмножество строк — делайте частичный индекс, как
`idx_outbox_pending`:

```sql
CREATE INDEX idx_outbox_pending ON outbox_events (next_retry_at)
    WHERE sent_at IS NULL AND dead_at IS NULL;
```

## 3. Применить и проверить обратимость

```bash
make migrate-up
make migrate-down     # откат на одну
make migrate-up       # и снова вперёд
```

## 4. Провести изменение по слоям

Порядок именно такой — снизу вверх:

1. **Домен** (`internal/domain/`) — поле в сущности. Домен без внешних
   зависимостей: ни pgx, ни сгенерированных моделей.
2. **Порт** (`internal/app/ports.go`) — если появился новый способ доступа.
3. **Репозиторий** (`internal/adapters/postgres/`) — SQL и скан.
   - список колонок держится одной константой (`orderColumns`,
     `restaurantColumns`), чтобы порядок в `SELECT` и в `Scan` не разъезжался;
   - ошибки оборачиваются `wrapDBError`, `pgx.ErrNoRows` превращается в
     доменную ошибку с конкретным кодом;
   - `r.db(ctx)` вместо `r.pool` — иначе запрос уйдёт мимо открытой транзакции.
4. **Use case** (`internal/app/`) — если меняется сценарий.
5. **Контракт** — если поле должно быть видно снаружи, см. скилл `api-contract`.

## 5. Тесты

Изменение схемы без интеграционного теста не считается завершённым.

```bash
make up                 # нужна живая БД
make test-integration
```

Тесты живут в `internal/adapters/postgres/integration_test.go` под тегом
`integration`. Каждый создаёт **своё** заведение через `env.seedRestaurant(t,
...)` со случайным slug — поэтому очистка БД между тестами не нужна и они не
мешают друг другу.

Если изменение касается консистентности (остатки, статусы, очереди) — тест
обязан быть конкурентным. Образец: `TestOrderService_Create_ConcurrentStockRace`
запускает 25 одновременных заказов на 10 порций и требует ровно 10 успехов.

## 6. Обновить документацию

- `docs/diagrams/erd.puml` — новая сущность, колонка или ограничение;
- `make diagrams` — перерендерить SVG (CI проверяет, что они не разошлись);
- README, раздел «Схема БД», если изменение заметное;
- ADR в `docs/adr/`, если решение неочевидно и его придётся объяснять.

## Чего не делать

- Не редактировать уже применённую миграцию — только новая поверх.
- Не писать down-миграцию заглушкой: нерабочий откат хуже отсутствующего,
  потому что создаёт ложную уверенность.
- Не добавлять `ON DELETE CASCADE` на связь, где каскад сотрёт исторические
  данные. В `order_items` намеренно `ON DELETE SET NULL` плюс снапшот названия и
  цены — см. ADR-0002.
