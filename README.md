# Авито.Кухня — MVP сервиса доставки еды

Backend-платформа, соединяющая две стороны: пользователей, которые заказывают
еду, и заведения, которые её готовят. Реализованы оба контура API, сервис-
эмулятор заведения и вся инфраструктура запуска.

Решение сделано как ответ на [тестовое задание](task.md); [промпт, по которому
велась разработка](prompt.md), приложен по просьбе из задания.

```bash
make up      # поднять стек
make smoke   # прогнать сквозной сценарий
```

## Что умеет сервис

**Для пользователя (B2C)**

- каталог заведений с курсорной пагинацией и режимом работы каждого;
- витрина меню, сгруппированная по категориям, с наличием и остатками;
- оформление заказа с защитой от повторов (`Idempotency-Key`);
- карточка заказа с позициями, зафиксированными ценами и таймлайном статусов;
- отмена заказа, пока заведение его не приняло.

**Для заведения (B2B)**

- полная синхронизация меню с версионированием;
- очередь заказов с фильтром по статусу;
- перевод заказа по конвейеру статусов;
- переключение режима работы кухни (`online` / `paused` / `closed`);
- получение вебхуков о новых заказах и отменах.

**Инфраструктура**

- гарантированная доставка событий заведениям (transactional outbox);
- автоматическая отмена заказов, на которые заведение не ответило;
- структурированные JSON-логи со сквозным `request_id`;
- корректная остановка без обрыва текущих заказов.

## Быстрый старт

**Требуется:** Docker с плагином Compose. Для локальных тестов и линтера — Go
1.25+; для рендера диаграмм — Java.

```bash
git clone <репозиторий> && cd avito-kitchen

make up      # postgres → migrate → api + restaurant-sim
make smoke   # 12 шагов сквозного сценария
```

После `make up`:

| Сервис | Адрес |
|---|---|
| API платформы | http://localhost:8080 |
| Сервис заведения | http://localhost:8081 |
| PostgreSQL | `localhost:5432`, `kitchen` / `kitchen` |

Проверка вручную:

```bash
curl -s localhost:8080/api/v1/restaurants | jq
curl -s localhost:8080/api/v1/restaurants/pizza-avito/menu | jq

curl -s -X POST localhost:8080/api/v1/orders \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"user_external_id":"usr_1","restaurant_id":1,
       "delivery_address":"ул. Ленина, 10",
       "items":[{"product_key":"pizza_margherita","qty":2}]}' | jq
```

Заказ примерно за 6 секунд сам пройдёт `NEW → ACCEPTED → COOKING → READY`:
`restaurant-sim` получает вебхук и ведёт его по конвейеру.

Остальные команды — `make help`.

## Пользовательские сценарии (CJM)

Диаграммы генерируются из исходников PlantUML: `make diagrams`.

### CJM пользователя

[`docs/diagrams/cjm_user.puml`](docs/diagrams/cjm_user.puml) ·
[SVG](docs/diagrams/cjm_user.svg)

Сценарий намеренно построен вокруг мест, где человек спотыкается, — именно они
определяют состав API:

| Шаг | Что происходит | Ответ API |
|---|---|---|
| 1 | Открывает каталог | `200` список с режимом работы и минимальной суммой |
| 2 | Смотрит меню | `200` категории, цены, остатки |
| 3 | Кладёт 12 пицц, а есть 10 | `409 OUT_OF_STOCK` с фактическим остатком |
| 4 | Убирает лишнее, но набирает 120 ₽ при минимуме 500 ₽ | `422 MIN_ORDER_NOT_MET` |
| 5 | Собирает корзину на 1330 ₽ | `201` номер заказа, статус `NEW` |
| 6 | У клиента оборвалась связь, запрос ушёл повторно | `201` **тот же** заказ |
| 7 | Следит за статусом | `200` таймлайн: `NEW → ACCEPTED → COOKING → READY` |
| 8 | Пытается отменить готовый заказ | `409 ORDER_CANNOT_BE_CANCELLED` |

Два продуктовых решения, заметных в этом сценарии:

- **Закрытые заведения видны в каталоге**, а не скрыты. Иначе человек собирает
  корзину и упирается в отказ, не понимая причины.
- **Недоступные позиции остаются в меню** с флагом `available: false`. Блюдо,
  которое «исчезло», выглядит как ошибка сайта; блюдо, помеченное «нет в
  наличии», — как понятное состояние.

### CJM заведения

[`docs/diagrams/cjm_restaurant.puml`](docs/diagrams/cjm_restaurant.puml) ·

Подключение → синхронизация меню → открытие кухни → приём вебхука → конвейер

### Жизненный цикл заказа

[`docs/diagrams/order_state_machine.puml`](docs/diagrams/order_state_machine.puml) ·
[SVG](docs/diagrams/order_state_machine.svg)

```
                   ┌─── restaurant ──→ ACCEPTED ──→ COOKING ──→ READY ──→ DELIVERED
                   │                       │           │
  [*] ──→ NEW ─────┼─── restaurant ──→ REJECTED        │
                   │                       ↑           ↓
                   └─── user | system ──→ CANCELLED ←──┘ (restaurant)
```

Граф — единственный источник правды по переходам
(`internal/domain/state_machine.go`). Его полнота зафиксирована тестом,
перебирающим всю матрицу 7 статусов × 7 статусов × 3 актора: разрешёнными
могут быть только девять перечисленных комбинаций.

Граница ответственности: **до `ACCEPTED` заказ отменяет пользователь, после —
только заведение**. Продукты уже в работе, и решение об отмене принимает тот,
кто несёт затраты.

Любой переход в `REJECTED` или `CANCELLED` возвращает списанные остатки в
каталог — в той же транзакции, что и смена статуса.

## Архитектура

### C4 Level 2 — контейнеры

[`docs/diagrams/c4_container.puml`](docs/diagrams/c4_container.puml) ·
[SVG](docs/diagrams/c4_container.svg)

```
   Пользователь            Оператор заведения
        │                          │
   ┌────▼─────┐            ┌───────▼──────────┐
   │Веб-клиент│            │ restaurant-sim   │
   │(вне MVP) │            │ меню, вебхуки,   │
   └────┬─────┘            │ статусы заказов  │
        │ REST             └───┬──────────▲───┘
        │                      │ B2B API  │ POST /kitchen/events
   ┌────▼──────────────────────▼──────────┴───┐
   │                  api                     │
   │  B2C + B2B HTTP, бизнес-логика, границы  │
   │  транзакций                              │
   │  ├─ outbox-воркер   (доставка событий)   │
   │  └─ reaper-воркер   (таймауты, уборка)   │
   └────────────────────┬─────────────────────┘
                        │ pgx/v5
                ┌───────▼────────┐   ┌──────────┐
                │  PostgreSQL 17 │◄──│ migrate  │
                └────────────────┘   └──────────┘
```

**Почему монолит.** Ключевой инвариант — атомарность связки «списать остаток +
создать заказ + записать событие». В одном процессе с одной базой это одна
транзакция. Разнесённое по сервисам, это распределённая сага с компенсациями,
которой на объёмах MVP нечего оптимизировать, зато есть что ломать.

**Почему воркеры внутри `api`.** Общий код, общий пул соединений, одна единица
деплоя. При этом аренда событий и `SKIP LOCKED` уже позволяют запускать
несколько экземпляров `api` параллельно — вынести воркеры в отдельный бинарник
можно, не трогая схему БД.

### Слои (Clean Architecture / Ports & Adapters)

```
cmd/api            cmd/restaurant-sim      точки входа, сборка зависимостей
        │
internal/adapters/ http · postgres · simclient      ← знают о HTTP и SQL
        │
internal/app/      use cases + порты (интерфейсы)   ← знают о домене
        │
internal/domain/   сущности, автомат, ошибки        ← не знает ни о чём
```

Зависимости направлены строго внутрь. `internal/domain` не импортирует ничего,
кроме стандартной библиотеки и `google/uuid`; `internal/app` объявляет порты, а
реализуют их адаптеры. Проверяется компилятором:

```go
var _ app.OrderRepo = (*OrderRepo)(nil)
```

| Пакет | Ответственность |
|---|---|
| `internal/domain` | Сущности, конечный автомат заказа, деньги, доменные ошибки |
| `internal/app` | Оркестрация сценариев, границы транзакций, воркеры, порты |
| `internal/adapters/postgres` | Репозитории на pgx/v5, менеджер транзакций |
| `internal/adapters/http` | Реализация strict-сервера, маппинг домен ↔ контракт |
| `internal/adapters/simclient` | HTTP-клиент доставки вебхуков заведению |
| `internal/platform` | Логгер, HTTP-сервер, прослойки, формат ошибок |
| `internal/gen` | Сгенерированный код — руками не редактируется |

## Схема базы данных

[`docs/diagrams/erd.puml`](docs/diagrams/erd.puml) ·
[SVG](docs/diagrams/erd.svg) · DDL: [`migrations/000001_init_schema.up.sql`](migrations/000001_init_schema.up.sql)

```
restaurants ──┬──< menus ──< products
              │                 ╎ (мягкая ссылка, ON DELETE SET NULL)
              └──< orders ──┬──< order_items
                            └──< order_status_events

idempotency_keys        outbox_events
(без связей)            (без FK — переживает удаление агрегата)
```

| Таблица | Назначение | Ключевые ограничения |
|---|---|---|
| `restaurants` | Заведения, режим работы, тарифы, хэш токена | `CHECK status IN (online, paused, closed)`, `UNIQUE api_key_hash` |
| `menus` | Версии меню | `UNIQUE (restaurant_id, version)`, частичный `UNIQUE (restaurant_id) WHERE published` |
| `products` | Позиции конкретной версии, цена и остаток | `UNIQUE (menu_id, product_key)`, `CHECK stock_qty >= 0` |
| `orders` | Заказы, суммы, версия для блокировки | `CHECK total = subtotal + fee`, `CHECK status IN (...)` |
| `order_items` | **Снапшот** позиций на момент заказа | `CHECK line_total = unit_price × qty` |
| `order_status_events` | История переходов | `CHECK actor IN (user, restaurant, system)` |
| `idempotency_keys` | Сохранённые ответы операций | `response_status = 0` — операция выполняется |
| `outbox_events` | Очередь событий заведениям | частичный индекс по неотправленным |

### Решения, заложенные в схему

**Деньги — целые копейки (`BIGINT`).** Ни `FLOAT`, ни `NUMERIC`: цена в
копейках — целое число по природе, а плавающая точка в деньгах — источник
расхождений на копейку в чеках.

**Инварианты продублированы `CHECK`-ограничениями.** `line_total_kopecks =
unit_price_kopecks * qty` проверяется и в коде, и в базе. Ошибка в приложении
не оставит некорректных данных.

**`orders.version` — оптимистичная блокировка.** Каждый переход статуса — это
`UPDATE ... WHERE id = ? AND version = ?` с инкрементом. Параллельное изменение
не затирается, а получает `409 STATE_CONFLICT`.

**`public_number` — UUIDv7.** Наружу отдаётся не автоинкремент: он раскрывает
количество заказов в системе. UUIDv7 при этом сортируем по времени создания,
поэтому индекс не деградирует, как на случайном UUIDv4.

**Частичные индексы под конкретные запросы.** Воркеру outbox нужны только
неотправленные события, reaper-у — только заказы в `NEW`:

```sql
CREATE INDEX idx_outbox_pending ON outbox_events (next_retry_at)
    WHERE sent_at IS NULL AND dead_at IS NULL;
CREATE INDEX idx_orders_stale_new ON orders (created_at) WHERE status = 'NEW';
```

**Ровно одно опубликованное меню** гарантируется частичным уникальным индексом,
а не проверкой в коде.

## Ключевые технические решения

Подробные разборы — в [`docs/adr/`](docs/adr/).

### Атомарное списание остатков — [ADR-0001](docs/adr/0001_postgresql_as_single_source_of_truth.md)

Главный инвариант: **нельзя продать больше порций, чем есть**. Проверка
встроена в `WHERE` самого `UPDATE`, поэтому между проверкой и списанием нет
окна для параллельной транзакции:

```sql
UPDATE products
SET stock_qty = stock_qty - $2
WHERE id = $1 AND available = TRUE
  AND (stock_qty IS NULL OR stock_qty >= $2)
RETURNING stock_qty;
```

Ноль затронутых строк → `OUT_OF_STOCK`. Списания внутри заказа идут по
возрастанию `product_id` — детерминированный порядок блокировок исключает
взаимную блокировку встречных заказов.

Отдельного Redis для остатков нет намеренно: два хранилища без общей транзакции
потребовали бы саги с компенсацией и сверкой, а выигрыш в скорости на объёмах
MVP не нужен.

Проверено тестом: 25 параллельных заказов на 10 порций → ровно 10 успехов,
15 отказов, остаток 0 и ни одной потерянной единицы.

### Версионирование меню и снапшоты — [ADR-0002](docs/adr/0002_menu_versioning_and_order_snapshots.md)

Синхронизация не правит существующие строки: она архивирует текущую версию и
создаёт `N+1`. Заказ хранит **копию** названия и цены, поэтому чек не меняется,
когда заведение поднимает цены или снимает блюдо с продажи.

Побочный эффект, разобранный в ADR: остаток привязан к версии меню, поэтому
отмена заказа после пересинхронизации — осознанный no-op. Прислав новое меню,
заведение заявило актуальные остатки, и дописывать туда порции из отменённого
заказа — значит спорить с источником правды.

### Transactional Outbox — [ADR-0003](docs/adr/0003_transactional_outbox_for_events.md)

Событие для заведения пишется **в ту же транзакцию**, что и заказ. Отправка
после `COMMIT` потерялась бы при сбое процесса; отправка внутри транзакции
неоткатываема. Outbox снимает двойную запись: обе строки ложатся вместе.

Воркер забирает события под `FOR UPDATE SKIP LOCKED` и сразу выдаёт **аренду** —
сдвигает `next_retry_at` вперёд, — поэтому транзакция не держится открытой на
время HTTP-запроса к заведению. Умер воркер посреди отправки — событие само
вернётся в очередь.

Повторы — экспоненциальный backoff с полным джиттером. Без джиттера пачка
событий вернулась бы синхронным залпом ровно в момент, когда заведение
поднимается.

Гарантия — **at-least-once**, поэтому вместе с событием уходит `X-Event-ID`, а
получатель обязан дедуплицировать.

### Идемпотентность создания заказа

`POST /api/v1/orders` требует `Idempotency-Key`. Ключ захватывается атомарным
`INSERT ... ON CONFLICT`, поэтому из параллельных запросов «первым» окажется
ровно один:

| Ситуация | Ответ |
|---|---|
| Первый запрос | выполняется, успешный ответ сохраняется |
| Повтор с тем же телом | сохранённый ответ, `Idempotent-Replay: true` |
| Тот же ключ, другое тело | `422 IDEMPOTENCY_PAYLOAD_MISMATCH` |
| Параллельный запрос с тем же ключом | `409 IDEMPOTENCY_IN_PROGRESS` |
| Заголовка нет | `400 IDEMPOTENCY_KEY_REQUIRED` |

Ответы с ошибкой не кэшируются, а захват освобождается: заказ, отклонённый из-за
нехватки остатка, клиент вправе повторить тем же ключом, когда остаток
пополнится.

### Аутентификация заведений — [ADR-0004](docs/adr/0004_partner_api_key_auth.md)

`X-Partner-Token`, в базе — только SHA-256 токена. Дамп базы не даёт доступа к
API. Поиск идёт по уникальному индексу на хэш, поэтому время ответа не зависит
от присланного токена.

`restaurant_id` берётся **только** из контекста, куда его положила прослойка, и
никогда из тела или пути — подделать чужой идентификатор невозможно. Для
операций над конкретным заказом дополнительно проверяется владение.

### Формат ошибок — RFC 7807

```json
{
  "type": "https://avito.ru/kitchen/errors/OUT_OF_STOCK",
  "title": "Conflict",
  "status": 409,
  "code": "OUT_OF_STOCK",
  "detail": "позиции «Пицца Маргарита» (ключ: pizza_margherita) осталось 5, а запрошено 12",
  "instance": "/api/v1/orders",
  "request_id": "c1f7a8e2-8921-4f3b-87b4-192a6c1a8e10"
}
```

Клиент принимает решения по машиночитаемому `code`, показывает человеку
`detail` и репортит проблему с `request_id`, по которому запрос находится в
логах одной командой.

Разделение статусов осмысленное: **409** — состояние каталога изменилось,
повтор с другой корзиной имеет смысл; **422** — запрос корректен, но нарушает
бизнес-правило.

### Автоматическая уборка

Фоновый reaper закрывает два долга, которые иначе копятся молча:

- заказ, на который заведение не ответило за `ORDER_ACCEPT_TIMEOUT`,
  отменяется от лица `system` с возвратом остатков — иначе он вечно держал бы
  зарезервированные порции;
- протухшие ключи идемпотентности удаляются по `expires_at`.

## API

Полная спецификация — [`api/openapi.yaml`](api/openapi.yaml) (OpenAPI 3.0).
Контракт первичен: типы, модели и strict-сервер генерируются из него через
`oapi-codegen` (`make gen`), а CI проверяет, что сгенерированный код не разошёлся
со спецификацией.

### Клиентские эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/v1/restaurants` | Каталог, курсорная пагинация, фильтр по режиму |
| `GET` | `/api/v1/restaurants/{slug}/menu` | Витрина меню по категориям |
| `POST` | `/api/v1/orders` | Оформление заказа (нужен `Idempotency-Key`) |
| `GET` | `/api/v1/orders/{public_number}` | Карточка заказа и таймлайн |
| `POST` | `/api/v1/orders/{public_number}/cancel` | Отмена пользователем |

### Партнёрские эндпоинты (`X-Partner-Token`)

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/partner/menu/sync` | Полная синхронизация меню (версия `N+1`) |
| `GET` | `/api/v1/partner/orders` | Очередь заказов заведения |
| `POST` | `/api/v1/partner/orders/{public_number}/status` | Перевод статуса |
| `POST` | `/api/v1/partner/kitchen-status` | Режим работы кухни |

### Служебные

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | Живость процесса |
| `GET` | `/readyz` | Готовность, включая доступность БД |

Проверки разные намеренно: `/health` не должен зависеть от БД, иначе
оркестратор перезапустит рабочий контейнер из-за недоступной базы; `/readyz`
снимает экземпляр с балансировки, пока зависимости не поднялись.

### Курсорная пагинация

Keyset по первичному ключу вместо `OFFSET`: стоимость запроса не растёт с
номером страницы, а вставка новых заведений не сдвигает границы уже отданных
страниц. Курсор непрозрачен (base64url) — клиент не должен строить логику на
его содержимом.

## Сервис заведения

`cmd/restaurant-sim` — отдельный бинарник в том же репозитории и модуле,
поднимается вместе со стеком. Играет роль реального партнёра и замыкает
интеграцию с обеих сторон.

**Собственное API**

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/kitchen/menu` | Эталонное меню заведения |
| `POST` | `/kitchen/events` | Вебхук от платформы |
| `GET` | `/health`, `/readyz` | Проверки |

**Что делает**

1. При старте дожидается готовности платформы (порядок контейнеров её не
   гарантирует) и синхронизирует своё меню.
2. Принимает вебхуки, **дедуплицируя по `X-Event-ID`**: доставка at-least-once,
   и повтор не должен второй раз отправить заказ на кухню. Помнит последние
   1000 идентификаторов.
3. Ведёт заказ по конвейеру `ACCEPTED → COOKING → READY` через партнёрское API.
4. Останавливает готовку, получив событие об отмене.
5. Корректно обрабатывает `409` — заказ успели отменить, это штатный исход
   гонки, а не сбой интеграции.

**Режимы для проверки сценариев**

| Переменная | Что воспроизводит |
|---|---|
| `SIM_AUTO_ACCEPT=false` | Заказ висит в `NEW` → срабатывает reaper |
| `SIM_REJECT_ALL=true` | Отказ заведения и возврат остатков |
| `SIM_ACCEPT_DELAY_MS`, `SIM_COOKING_TIME_MS`, `SIM_READY_DELAY_MS` | Скорость конвейера |

## Тестирование

```bash
make test              # модульные, с детектором гонок
make up
make test-integration  # интеграционные против настоящего PostgreSQL
make smoke             # сквозной сценарий по поднятому стеку
```

### Модульные — `internal/domain`, `internal/app`

Бизнес-правила на фейковых репозиториях, без базы. Фейковый менеджер транзакций
воспроизводит главное свойство настоящего: при ошибке изменения откатываются,
— поэтому проверять откат частичного списания можно и здесь.

Отдельно стоит отметить тест конечного автомата: он перебирает **всю матрицу**
7 × 7 × 3 и требует, чтобы разрешёнными были ровно девять заявленных переходов.
Случайно расширить граф при рефакторинге не получится. Второй тест проверяет,
что из любого нетерминального статуса достижим терминальный — то есть в
жизненном цикле нет ловушек.

### Интеграционные — `internal/adapters/postgres` (тег `integration`)

Проверяют ровно то, что нельзя проверить на фейках:

| Тест | Что доказывает |
|---|---|
| `Create_ConcurrentStockRace` | 25 параллельных заказов на 10 порций → ровно 10 успехов, остаток 0, ничего не потеряно |
| `ChangeStatus_ConcurrentTransitions` | 8 параллельных переходов → заказ покидает `NEW` ровно один раз |
| `ClaimBatch_ConcurrentWorkersDoNotOverlap` | 4 воркера не получают одно событие дважды |
| `PublishVersion_ConcurrentSyncsSerialize` | 6 одновременных синхронизаций не ломают нумерацию версий |
| `Reserve_ConcurrentClaimIsExclusive` | Ключ идемпотентности захватывает ровно один из 16 запросов |
| `Migrations_AreReversible` | `down` до нуля и `up` обратно работают |
| `CancelAfterMenuResyncIsNoop` | Краевой случай из ADR-0002 ведёт себя как задокументировано |

Каждый тест создаёт своё заведение со случайным slug, поэтому очистка базы
между тестами не нужна и они не мешают друг другу.

### Сквозной — `scripts/smoke.sh`

12 шагов от готовности сервисов до закрытия кухни, каждый с проверкой
HTTP-статуса и доменного `code`. Проверяет не «отвечает ли сервис», а
бизнес-сценарии целиком: отказ сверх остатка, недобор минимальной суммы,
идемпотентный повтор, расхождение тела под тем же ключом, доставку события до
заведения и автоматический конвейер, таймлайн из четырёх событий, позднюю
отмену, закрытие кухни.

## Конфигурация

Все параметры — через переменные окружения, шаблон в
[`.env.example`](.env.example). Конфигурация валидируется на старте, и все
ошибки собираются разом: сервис либо стартует полностью настроенным, либо не
стартует вовсе.

Наиболее содержательные:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `DATABASE_URL` | — | Обязательна |
| `OUTBOX_POLL_INTERVAL` | `500ms` | Как часто воркер опрашивает очередь |
| `OUTBOX_MAX_ATTEMPTS` | `10` | После скольких неудач событие снимается с доставки |
| `OUTBOX_LEASE` | `30s` | Аренда события; **обязана быть больше** `OUTBOX_HTTP_TIMEOUT` |
| `ORDER_ACCEPT_TIMEOUT` | `5m` | Через сколько платформа отменит неподтверждённый заказ |
| `IDEMPOTENCY_TTL` | `24h` | Сколько живёт сохранённый ответ |

Связь `OUTBOX_LEASE > OUTBOX_HTTP_TIMEOUT` проверяется явно: при обратном
соотношении аренда истекала бы раньше, чем воркер дождался ответа, и событие
уходило бы дважды на ровном месте.

## Упрощения MVP и что делать дальше

Задание просит не гнаться за production-ready решением, поэтому часть вещей
сознательно не сделана. Ниже — что именно, почему это допустимо сейчас и чем
обернётся при росте.

### Осознанно не реализовано

| Упрощение | Почему допустимо в MVP | Что делать дальше |
|---|---|---|
| **Нет аутентификации пользователей** | Явно исключена заданием; `user_external_id` приходит как внешний идентификатор экосистемы Авито | JWT от общего провайдера; проверка владения заказом |
| **Токены заведений предсказуемы** (`dev-partner-token`) | Демо-окружение обязано подниматься одной командой без ручной настройки секретов | Криптографическая генерация, выдача один раз, хранение в секрет-менеджере |
| **Один токен на заведение, без ротации** | Список партнёров закрытый и небольшой | Таблица `restaurant_api_keys` с `expires_at` и несколькими активными ключами |
| **Нет rate limiting** | Нет внешнего трафика | Ограничение на уровне шлюза |
| **Нет платежей** | Вне объёма задания | Отдельный контур с холдированием средств; статус `PAID` в автомате |
| **Нет курьеров и геолокации** | Вне объёма | Отдельный домен доставки; `READY → PICKED_UP → DELIVERED` |
| **Нет метрик и трейсинга** | Логи со сквозным `request_id` покрывают отладку MVP | Prometheus (RED-метрики, глубина outbox), OpenTelemetry |
| **Нет уборки доставленных событий** | Объёмы малы | Партиционирование `outbox_events` по времени или периодическое удаление |
| **CORS открыт (`*`)** | Клиента ещё нет | Явный список доменов |
| **Поиск и фильтры каталога** | Не влияют на демонстрируемые инварианты | Полнотекстовый поиск, сортировка по расстоянию и рейтингу |

### Известные ограничения архитектуры

**Популярная позиция — точка сериализации.** Все заказы на одно блюдо ждут
строчной блокировки. На объёмах MVP несущественно; при росте — шардирование
остатка на N строк-«корзин» или отдельная таблица резервов с TTL.

**Остаток привязан к версии меню.** Разобрано в
[ADR-0002](docs/adr/0002_menu_versioning_and_order_snapshots.md): отмена заказа
после пересинхронизации меню не возвращает остаток. В проде — резервы,
привязанные к `product_key`, а не к строке конкретной версии.

**`products` растёт линейно по числу синхронизаций.** Нужна архивация версий,
на которые уже не ссылается ни один заказ.

**Постоянный опрос базы воркерами.** При росте нагрузки — `LISTEN/NOTIFY`:
воркер просыпается по сигналу вместо тика.

**Запись упирается в один инстанс PostgreSQL.** Реплики помогут витрине, но не
оформлению заказов. Дальше — шардирование по `restaurant_id`.

### Что готово к росту без переписывания

- **Несколько экземпляров `api`** запускаются уже сейчас: `SKIP LOCKED` и
  аренда корректны при любом их числе.
- **Вынос воркеров в отдельный бинарник** не требует изменений схемы БД.
- **Переход на брокер** меняет только реализацию порта `EventDeliverer` —
  outbox становится источником для Kafka вместо HTTP.
- **Замена хранилища** ограничена пакетом `internal/adapters/postgres`: домен и
  use cases о PostgreSQL не знают.
