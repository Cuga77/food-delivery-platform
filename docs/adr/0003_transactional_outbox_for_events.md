# ADR-0003. Transactional Outbox для доставки событий заведениям

- **Статус:** принято
- **Дата:** 2026-08-26
- **Контекст решения:** MVP Авито.Кухня

## Контекст

Когда пользователь оформляет заказ, заведение должно об этом узнать — иначе
заказ есть в базе, деньги зарезервированы, а на кухне о нём не подозревают.

Задача выглядит тривиально: после `COMMIT` отправить HTTP-запрос заведению.
Проблема в том, что «после COMMIT» — это уже за пределами транзакции, и всё,
что происходит там, может не произойти вовсе: процесс умрёт, сеть моргнёт,
заведение окажется в перезапуске. Заказ останется висеть в `NEW`, пока его не
отменит reaper по таймауту, а клиент всё это время будет ждать.

## Варианты

### 1. Отправка вебхука прямо из хендлера

```go
tx.Commit()
httpClient.Post(restaurant.URL, event) // ← здесь всё и ломается
```

- **За:** минимум кода, событие уходит мгновенно.
- **Против:** событие теряется при любом сбое между коммитом и отправкой —
  и восстановить его неоткуда, в базе нет следа о том, что отправка требовалась.
  Плюс время ответа заведения становится временем ответа нашего API: медленная
  кухня замедляет оформление заказа для клиента.

### 2. Отправка внутри транзакции

- **За:** «атомарно».
- **Против:** это не атомарность, а её иллюзия: HTTP-запрос откатить нельзя.
  Заведение получит заказ, транзакция упадёт, заказа не будет. Плюс транзакция
  держится открытой на время сетевого запроса — блокировки на строках товаров
  висят секундами.

### 3. Брокер сообщений (Kafka / RabbitMQ)

- **За:** промышленный стандарт, готовые ретраи и мониторинг.
- **Против:** ровно та же проблема двойной записи — «закоммитить в PostgreSQL и
  опубликовать в Kafka» атомарно тоже нельзя. Брокер её не решает, а переносит.
  Плюс это ещё один контейнер, ещё одна точка отказа и операционная нагрузка
  ради одного типа события в MVP.

### 4. Transactional Outbox (выбран)

## Решение

Событие записывается **в ту же транзакцию**, что и заказ, — в таблицу
`outbox_events`. Отправкой занимается фоновый воркер.

```
BEGIN
  списание остатков
  INSERT INTO orders ...
  INSERT INTO order_items ...
  INSERT INTO order_status_events ...
  INSERT INTO outbox_events (event_type='order_created', payload=...)
COMMIT
```

Двойной записи нет: обе строки ложатся одной транзакцией. Либо есть и заказ, и
событие, либо ничего.

### Выборка с арендой

```sql
WITH claimed AS (
    SELECT id FROM outbox_events
    WHERE sent_at IS NULL AND dead_at IS NULL AND next_retry_at <= NOW()
    ORDER BY id
    LIMIT $1
    FOR UPDATE SKIP LOCKED
)
UPDATE outbox_events o
SET next_retry_at = NOW() + make_interval(secs => $2)
FROM claimed c
WHERE o.id = c.id
RETURNING o.id, o.aggregate_type, o.aggregate_id, o.event_type,
          o.payload, o.attempts, o.next_retry_at, o.created_at;
```

Один запрос делает три вещи:

- **`FOR UPDATE SKIP LOCKED`** — строки, захваченные соседним воркером,
  пропускаются, а не ждут. Несколько экземпляров `api` разгребают очередь
  параллельно и не блокируют друг друга.
- **Сдвиг `next_retry_at` вперёд** — это аренда: событие не будет выдано
  повторно, пока текущий воркер его доставляет.
- **`RETURNING`** — содержимое приходит сразу, второй запрос не нужен.

### Почему аренда, а не открытая транзакция

Прямолинейная реализация паттерна держит транзакцию открытой всё время
доставки: `SELECT ... FOR UPDATE SKIP LOCKED` → HTTP → `UPDATE sent_at` →
`COMMIT`. Это работает, но плохо стареет:

- транзакция живёт столько же, сколько HTTP-запрос к чужому сервису, — секунды
  на каждое событие;
- соединение из пула занято всё это время;
- долгая транзакция удерживает горизонт видимости и мешает autovacuum.

Аренда снимает всё это: транзакция закрывается сразу после захвата, доставка
идёт вне её. Если воркер умрёт посреди отправки, событие само вернётся в
очередь по истечении аренды. Конфигурация проверяет `OUTBOX_LEASE >
OUTBOX_HTTP_TIMEOUT` на старте — иначе аренда истекла бы раньше, чем воркер
дождался ответа.

### Повторы

Неудача (`5xx`, таймаут, отказ соединения) увеличивает `attempts` и переносит
`next_retry_at` с экспоненциальным ростом задержки и **полным джиттером**:
задержка выбирается равномерно из `[0, base × 2^attempts]`, с потолком
`OUTBOX_MAX_BACKOFF`. Джиттер обязателен: без него пачка событий, отвалившаяся
из-за недоступности заведения, вернётся синхронным залпом ровно в тот момент,
когда оно поднимается.

После `OUTBOX_MAX_ATTEMPTS` событие помечается `dead_at` и снимается с доставки.
Строка **не удаляется** — она остаётся свидетельством инцидента с сохранённым
`last_error`, с которого начинается разбор.

## Гарантия доставки

**At-least-once.** Событие не может потеряться, но может прийти дважды: если
доставка прошла, а `UPDATE sent_at` не успел, после истечения аренды событие
уйдёт повторно.

Exactly-once на границе двух систем недостижим в принципе, поэтому
ответственность за дедупликацию явно передана получателю: вместе с событием
уходит заголовок `X-Event-ID` с идентификатором строки outbox. `restaurant-sim`
помнит последние 1000 идентификаторов и отвечает на повтор `204`, не запуская
работу заново.

## Последствия

**Хорошее**

- Событие не теряется ни при каком сбое: оно уже в базе.
- Время ответа API не зависит от скорости заведения.
- Горизонтальное масштабирование даётся бесплатно: `SKIP LOCKED` + аренда
  корректны при любом числе экземпляров `api`.
- Диагностируемость: очередь — обычная таблица. `SELECT * FROM outbox_events
  WHERE sent_at IS NULL` отвечает на вопрос «что не доехало» без внешних
  инструментов.

**Плохое**

- Доставка не мгновенная: задержка до `OUTBOX_POLL_INTERVAL` (500 мс).
- Постоянный фоновый опрос базы. При росте нагрузки лечится `LISTEN/NOTIFY` —
  воркер просыпается по сигналу вместо тика.
- Таблица растёт. Нужна периодическая уборка доставленных событий (в MVP не
  реализована — отмечено в README как упрощение).

**Когда пересматривать**

Когда типов событий станет много, а потребителей — больше одного, outbox
превращается в источник для брокера: воркер публикует в Kafka, а не шлёт HTTP.
Схема к этому готова — меняется только реализация `EventDeliverer`.
