# ADR-0002. Версионирование меню и снапшоты позиций в заказе

- **Статус:** принято
- **Дата:** 2026-08-26
- **Контекст решения:** MVP Авито.Кухня

## Контекст

Заведение управляет своим меню само и присылает его целиком через
`POST /api/v1/partner/menu/sync`. Меню меняется часто: обновились цены, кончился
ингредиент, сняли блюдо с продажи.

Отсюда два вопроса, на которые схема БД обязана ответить однозначно:

1. Что происходит с позициями, которых больше нет в присланном меню, если на
   них ссылаются заказы двухмесячной давности?
2. Что видит пользователь в истории заказов, если цена блюда с тех пор выросла?

Ответ «цену в чеке пересчитаем по текущему меню» неприемлем: чек — финансовый
документ, он не имеет права меняться задним числом.

## Варианты

### 1. Обновление меню на месте (UPSERT + удаление лишних)

- **За:** одна версия меню, простые запросы, минимум строк.
- **Против:** удаление позиции ломает исторические заказы. `ON DELETE RESTRICT`
  сделает невозможным снятие блюда с продажи, `ON DELETE CASCADE` сотрёт
  позиции старых заказов, `SET NULL` оставит заказ без названия и цены.
  Изменение цены переписывает историю.

### 2. Soft delete + история цен отдельной таблицей

- **За:** позиции не пропадают, цены версионируются.
- **Против:** каждый запрос витрины обязан помнить про `deleted_at` и выбирать
  цену «на дату» — забытое условие тихо ломает выдачу. Появляется temporal-join
  там, где нужен обычный `SELECT`.

### 3. Версионирование меню + снапшот в заказе (выбран)

## Решение

**Меню версионируется целиком.** Синхронизация не меняет существующие строки:
она архивирует текущую версию и создаёт новую с номером `N+1`.

```sql
UPDATE menus SET status = 'archived'
WHERE restaurant_id = $1 AND status = 'published';

INSERT INTO menus (restaurant_id, version, status)
VALUES ($1, (SELECT COALESCE(MAX(version), 0) + 1 FROM menus WHERE restaurant_id = $1),
        'published');
```

Ровно одна опубликованная версия у заведения гарантируется частичным уникальным
индексом:

```sql
CREATE UNIQUE INDEX idx_menus_restaurant_active
    ON menus (restaurant_id) WHERE status = 'published';
```

Одновременные синхронизации сериализуются блокировкой строки заведения
(`SELECT ... FOR UPDATE`) — иначе обе вычислили бы одинаковый `N+1` и одна
упала бы на уникальном индексе.

**Заказ хранит снапшот позиций.** В `order_items` копируются название и цена на
момент оформления:

| Поле | Назначение |
|---|---|
| `product_id` | мягкая ссылка на позицию, `ON DELETE SET NULL` |
| `product_key` | артикул заведения — переживает любые версии |
| `product_name_snapshot` | название на момент заказа |
| `unit_price_kopecks` | цена на момент заказа |
| `line_total_kopecks` | `CHECK (line_total = unit_price * qty)` |

Чек читается целиком, даже если позиция давно исчезла из каталога.

## Последствия

**Хорошее**

- Исторические заказы неизменны по построению, а не по договорённости.
- Витрина — простой запрос по одной опубликованной версии, без условий на
  «удалённость» и без temporal-join.
- Откат меню сводится к смене статусов версий.
- Полная замена совпадает с ментальной моделью партнёра: «вот моё меню», а не
  «вот дельта к тому, что вы у себя помните». Отсутствие позиции в присланном
  меню однозначно означает, что позиции больше нет.

**Плохое**

- Таблица `products` растёт линейно по числу синхронизаций. На объёмах MVP
  несущественно; в проде — периодическая архивация версий, на которые уже не
  ссылается ни один заказ.
- **Остаток привязан к версии меню.** Это главный компромисс решения, и он
  требует отдельного разбора.

## Краевой случай: отмена заказа после пересинхронизации меню

Сценарий:

1. клиент заказал 3 пиццы — `stock_qty` позиции версии 1 упал с 10 до 7;
2. заведение прислало новое меню — версия 1 ушла в архив, появилась версия 2
   со своими остатками;
3. клиент отменил заказ.

Куда возвращать три порции? Позиция, с которой их списали, принадлежит архивной
версии, и её остаток на витрину больше не влияет.

**Принятое поведение:** возврат применяется только к позициям опубликованного
меню, иначе это осознанный no-op:

```sql
UPDATE products p
SET stock_qty = p.stock_qty + $2
FROM menus m
WHERE p.id = $1 AND m.id = p.menu_id
  AND m.status = 'published'
  AND p.stock_qty IS NOT NULL;
```

Обоснование: прислав новое меню, заведение заявило актуальные остатки. Долить
туда порции из отменённого заказа — значит переписать то, что заведение только
что о себе сообщило. Источник правды по остаткам — заведение, а не история
отмен платформы.

Поведение зафиксировано тестом
`TestOrderService_ChangeStatus_CancelAfterMenuResyncIsNoop`.

**Как это выглядело бы в проде.** Отдельная таблица резервов, живущая не в
каталоге, а рядом с заказом: `reservations (order_id, product_key, qty, state)`.
Резерв привязан к `product_key`, а не к строке конкретной версии меню, поэтому
переживает пересинхронизацию. Для MVP это лишний слой: демонстрируемый инвариант
(«не продать больше, чем есть») достигается и без него, а связка «остаток живёт
на позиции меню» на порядок проще читается.
