# ADR-0004. Аутентификация заведений по статическому токену

- **Статус:** принято
- **Дата:** 2026-08-26
- **Контекст решения:** MVP Авито.Кухня

## Контекст

B2B-контур позволяет заведению перевыложить меню, увидеть очередь заказов и
менять их статусы. Доступ к нему должен быть закрытым: чужое заведение не должно
ни читать заказы, ни управлять ими.

Аутентификация **пользователей** заданием явно исключена из объёма — клиентские
эндпоинты остаются открытыми. Аутентификация **заведений** — нет: без неё
партнёрское API просто не имеет смысла, потому что не к чему привязать
`restaurant_id`.

В MVP список заведений закрытый и заводится администратором площадки: это не
самообслуживаемая регистрация, а несколько десятков известных партнёров.

## Варианты

### 1. OAuth 2.0 / OIDC

- **За:** индустриальный стандарт, ротация токенов, скоупы, отзыв.
- **Против:** требует сервер авторизации, поток выдачи, обновление токенов и
  реализацию на стороне каждого заведения. Для закрытого списка партнёров в
  MVP — несопоставимая цена за возможности, которые ещё некому использовать.

### 2. mTLS

- **За:** сильнейшая из вариантов аутентификация, привязка к ключу.
- **Против:** нужен собственный CA, выдача и ротация клиентских сертификатов,
  терминация TLS с проверкой клиента. Порог входа для партнёра высокий: не
  каждая пиццерия имеет инженера, способного настроить клиентский сертификат.

### 3. Подпись запроса (HMAC по телу и timestamp)

- **За:** защищает от повтора и подмены тела, секрет не ходит по сети.
- **Против:** заметно сложнее в интеграции (канонизация запроса, окно времени,
  расхождение часов). Даёт выигрыш в основном там, где канал не защищён; при
  HTTPS основная угроза — утечка секрета, а не перехват.

### 4. Статический токен в заголовке (выбран)

## Решение

Заведение присылает `X-Partner-Token: <token>`. В базе хранится **только
SHA-256 токена в hex**, сам токен — никогда.

```sql
api_key_hash CHAR(64) NOT NULL
```

```go
func HashToken(token string) string {
    sum := sha256.Sum256([]byte(token))
    return hex.EncodeToString(sum[:])
}
```

Поиск заведения идёт по уникальному индексу на `api_key_hash` — одним обращением
к индексу, а не перебором строк с посимвольным сравнением. Побочный эффект
приятный: время ответа не зависит от того, насколько «близок» присланный токен к
настоящему, так что подобрать его по таймингам нельзя.

### Что даёт хранение хэша

Дамп базы не даёт доступа к API. Утёкший `api_key_hash` бесполезен: чтобы
пройти аутентификацию, нужен прообраз, а SHA-256 необратим.

### Почему именно SHA-256, а не bcrypt/argon2

Для паролей медленный хэш обязателен: пароли выбирают люди, они короткие и
предсказуемые, и перебор по словарю реален. Партнёрский токен — случайная строка
высокой энтропии, выданная площадкой; словарной атаки на неё не существует, а
перебор пространства 128+ бит невозможен независимо от скорости хэша. Зато
быстрый хэш здесь принципиален: он считается на **каждом** партнёрском запросе,
и bcrypt превратил бы аутентификацию в самую дорогую часть обработки.

### Изоляция данных между заведениями

Аутентификации мало — нужна авторизация. `restaurant_id` берётся **только** из
контекста, куда его положила прослойка `PartnerAuth`, и никогда из тела или пути
запроса:

```go
restaurant, ok := middleware.RestaurantFromContext(ctx)
```

Подделать чужой `restaurant_id` в запросе невозможно — его там просто нет. Для
операций над конкретным заказом дополнительно проверяется владение:

```go
if change.RestaurantID != 0 && order.RestaurantID != change.RestaurantID {
    return domain.Errorf(domain.CodeForbidden, ...)
}
```

Ответ — `403 FORBIDDEN` без деталей о чужом заказе. Проверка зафиксирована
тестами `TestOrderService_ChangeStatus_ForeignOrderIsForbidden` и
`TestOrderService_ChangeStatus_ForeignRestaurantForbidden`.

### Гигиена токена

- Токен не логируется — в записях остаётся только `slug` опознанного заведения.
- Токен не попадает в ответы API.
- Заголовок, а не query-параметр: query-строки оседают в логах прокси и в
  истории браузера.

## Последствия

**Хорошее**

- Порог интеграции для партнёра — один заголовок.
- Утечка дампа БД не компрометирует доступ.
- Аутентификация — один поиск по уникальному индексу.
- Схема данных не мешает эволюции: добавить второй токен для ротации — это
  вынести хэши в отдельную таблицу `restaurant_api_keys`.

**Плохое и осознанно принятое**

- **Нет ротации без простоя.** У заведения ровно один действующий токен; смена
  требует согласованного обновления с обеих сторон. Лечится таблицей ключей с
  `expires_at` и поддержкой нескольких активных.
- **Нет скоупов.** Токен даёт полный доступ к партнёрскому контуру: и меню, и
  заказы. Разделение «только чтение очереди» / «управление статусами» в MVP не
  требуется.
- **Нет ограничения частоты запросов.** Скомпрометированный токен позволяет
  сколько угодно вызовов. В проде — rate limiting на уровне шлюза.
- **Токены демо-заведений предсказуемы** (`dev-partner-token`) и лежат в
  `migrations/000002_seed_demo.up.sql` и `docker-compose.yml`. Это осознанное
  упрощение локального окружения: стек должен подниматься одной командой без
  ручной настройки секретов. В проде токены генерируются криптографическим
  генератором и выдаются партнёру один раз.
- **HTTPS не терминируется приложением.** Токен защищён от перехвата только при
  наличии TLS перед сервисом. В MVP compose поднимает голый HTTP на localhost.
