# ADR-0001. PostgreSQL как единственный источник правды

- **Статус:** принято
- **Дата:** 2026-08-26
- **Контекст решения:** MVP Авито.Кухня

## Контекст

Центральный инвариант сервиса: **нельзя продать больше порций, чем есть на
кухне**. Заказ считается оформленным только если одновременно выполнено пять
вещей:

1. заведение принимает заказы;
2. все позиции есть в опубликованном меню и доступны;
3. остатки списаны;
4. сумма прошла проверку минимального заказа;
5. заказ, снапшот позиций и событие для заведения записаны.

Нарушение атомарности здесь стоит дорого в обе стороны: списанный остаток без
заказа — потерянная выручка и «фантомный» дефицит; заказ без списания — двойная
продажа последней пиццы и разбирательство с клиентом.

Типовой для таких задач подход — держать остатки в Redis (быстрые атомарные
`DECRBY`), а заказы в реляционной БД. Рассматривались три варианта.

## Варианты

### 1. Redis для остатков + PostgreSQL для заказов

- **За:** списание остатка — операция за микросекунды, база не становится
  узким местом при всплеске заказов.
- **Против:** два хранилища без общей транзакции. Между `DECRBY` в Redis и
  `INSERT` в PostgreSQL появляется окно, в котором процесс может умереть.
  Закрывать его пришлось бы сагой с компенсацией, сверкой остатков и
  обработкой «зависших» резервов — то есть писать распределённую транзакцию
  руками. Плюс Redis по умолчанию не durable: перезапуск с потерей последних
  записей AOF означает разъехавшиеся остатки.

### 2. Оптимистичная проверка остатка в приложении

Прочитать `stock_qty`, сравнить в Go, записать новое значение.

- **За:** просто и очевидно читается.
- **Против:** классическая гонка read-modify-write. Между `SELECT` и `UPDATE`
  вклинивается параллельная транзакция, и остаток уходит в минус. Лечится
  либо блокировкой строки, либо переносом проверки в SQL — то есть вариантом 3.

### 3. PostgreSQL как единственное хранилище (выбран)

Всё — заведения, версии меню, остатки, заказы, история статусов, ключи
идемпотентности и очередь исходящих событий — живёт в одной базе, и весь
сценарий оформления выполняется в одной транзакции.

## Решение

Используем **PostgreSQL 17 как единственный источник правды**. Списание
остатка выражено одним запросом, где проверка встроена в `WHERE`:

```sql
UPDATE products
SET stock_qty = stock_qty - $2
WHERE id = $1
  AND available = TRUE
  AND (stock_qty IS NULL OR stock_qty >= $2)
RETURNING stock_qty;
```

Между проверкой и списанием нет окна: PostgreSQL блокирует строку на время
транзакции, поэтому конкурирующие заказы на последнюю порцию выстраиваются в
очередь, и второй получает ноль затронутых строк → `OUT_OF_STOCK`.

Дополнительно:

- **Детерминированный порядок блокировок.** Списания внутри заказа идут по
  возрастанию `product_id`. Без этого два встречных заказа на пересекающиеся
  корзины могли бы заблокировать друг друга (deadlock).
- **Инварианты продублированы в схеме.** `CHECK (stock_qty >= 0)`,
  `CHECK (total_kopecks = subtotal_kopecks + delivery_fee_kopecks)`,
  `CHECK (line_total_kopecks = unit_price_kopecks * qty)`. Даже ошибка в коде
  не оставит базу в некорректном состоянии.
- **Уровень изоляции — Read Committed** (по умолчанию). Serializable не нужен:
  все критичные проверки выражены в самих `UPDATE` и защищены строчными
  блокировками, а не read-modify-write в приложении.

## Последствия

**Хорошее**

- Атомарность даётся движком БД, а не самописной сагой: откат отменяет и
  списания, и заказ, и событие.
- Один источник правды — нет расхождений между хранилищами и не нужна сверка.
- Тестируемо: гонка воспроизводится интеграционным тестом
  (`TestOrderService_Create_ConcurrentStockRace`), который запускает 25
  параллельных заказов на 10 порций и проверяет, что успешных ровно 10.

**Плохое**

- Популярная позиция становится точкой сериализации: все заказы на неё ждут
  строчной блокировки. На объёмах MVP это несущественно, при росте лечится
  шардированием остатка на N строк-«корзин» или переходом на резервы с TTL.
- Запись упирается в один инстанс PostgreSQL. Реплики читателя помогут витрине,
  но не оформлению заказов.

**Когда пересматривать**

Если профиль нагрузки покажет, что ожидание строчной блокировки на топовых
позициях становится заметным для пользователя, — вводить отдельную таблицу
резервов с TTL и шардированием остатка. Схема к этому готова: остаток уже
изолирован в `products`, а не размазан по заказам.
