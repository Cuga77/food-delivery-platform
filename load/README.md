# Нагрузочные сценарии (k6)

Три сценария, каждый отвечает на свой вопрос:

| Файл | Вопрос |
|---|---|
| [`browse.js`](browse.js) | держит ли витрина поток чтения и не дорожает ли пагинация с глубиной |
| [`order.js`](order.js) | какова пропускная способность пути записи — транзакции оформления заказа |
| [`contention.js`](contention.js) | **не перепродаём ли мы товар**, когда за последние порции дерутся десятки клиентов |

Третий — главный. Это не замер производительности, а проверка ключевого
инварианта системы снаружи, через HTTP, с сетью и пулом соединений в цепочке.
Интеграционный тест проверяет то же самое на 25 горутинах внутри процесса;
здесь — на 60 виртуальных пользователях через реальный сервер.

## Запуск

Нужен [k6](https://k6.io/docs/get-started/installation/). Если его нет, а Go
есть:

```bash
GOBIN=$PWD/bin go install go.k6.io/k6@latest
```

Дальше — при поднятом стеке (`make up`):

```bash
make load            # все три сценария подряд
make load-browse     # только чтение
make load-order      # только запись
make load-contention # только гонка за остатком
```

Или напрямую, с параметрами:

```bash
k6 run -e RATE=300 -e DURATION=1m load/browse.js
k6 run -e RATE=200 -e DURATION=1m load/order.js
k6 run -e STOCK=500 -e ITERATIONS=1500 -e VUS=100 load/contention.js
```

| Переменная | Где | По умолчанию | Смысл |
|---|---|---|---|
| `BASE_URL` | везде | `http://localhost:8080` | адрес сервиса |
| `PARTNER_TOKEN` | везде | `dev-partner-token` | токен для подготовки меню |
| `RATE` | browse, order | 100 / 30 | целевая интенсивность в **итерациях** в секунду (см. ниже) |
| `DURATION` | browse, order | `30s` | длительность плато |
| `STOCK` | contention | 200 | сколько порций выложить |
| `ITERATIONS` | contention | 600 | сколько попыток заказать |
| `VUS` | contention | 60 | сколько клиентов дерётся за товар |
| `SPREAD` | contention | 1 | на сколько позиций разнести тот же остаток |
| `MAX_ACCEPTED_P95` / `MAX_ACCEPTED_P99` | contention | 300 / 400 мс | пороги задержки успешного заказа |
| `MAX_REJECTED_P95` / `MAX_REJECTED_P99` | contention | 200 / 300 мс | пороги задержки отказа |
| `PROFILE` | order | ступени | `constant` — ровная интенсивность вместо разгона |

## Что важно знать перед прогоном

**Сценарий сам готовит себе каталог.** Каждый `setup()` публикует новую версию
меню через партнёрское API: остатки и цены должны быть известны точно, иначе
результат зависит от того, что осталось от предыдущих прогонов. Побочный
эффект — после нагрузки в каталоге лежит нагрузочное меню. Вернуть демо-данные:

```bash
docker compose restart restaurant-sim   # он синхронизирует эталонное меню
# или полностью с нуля:
make down-v && make up
```

**Отключите автоприёмку заказов у симулятора.** Иначе каждый созданный заказ
породит ещё три запроса смены статуса, и вы будете мерить таймеры
`restaurant-sim`, а не платформу:

```bash
SIM_AUTO_ACCEPT=false docker compose up -d --force-recreate restaurant-sim
```

**409 и 422 — не ошибки, но только в сценариях записи.** `order.js` и
`contention.js` расширяют список ожидаемых статусов: иначе метрика ошибок
перестала бы отличать сбой сервиса от корректного отказа в заказе, а в
`contention.js` две трети ответов именно такие. `browse.js` этого послабления
**не** получает: витрина не должна отвечать ни 409, ни 422 никогда, и если
ответила — это настоящая ошибка, прятать её нельзя.

**`RATE` — это итерации в секунду, а не запросы.** В `constant-arrival-rate`
k6 нормирует итерации, а итерация `browse.js` делает один-два запроса. Реальный
запросный RPS выше указанного примерно в 1,25 раза. У `order.js` итерация —
один заказ плюс чтение карточки в каждом десятом случае.

**Что входит в замеряемый путь записи.** Оформление заказа — это не только
транзакция с остатками: прослойка идемпотентности делает `INSERT` ключа перед
операцией и `UPDATE` (при успехе) либо `DELETE` (при отказе) после неё. Цифры
ниже включают эти обращения — так же, как их видит настоящий клиент.

**Потолок 2400/с — транзакционный, а не сквозной.** Outbox-воркер забирает по
50 событий за проход и доставляет их последовательно синхронным HTTP. При
такой интенсивности заказов очередь `outbox_events` будет расти быстрее, чем
разгребается: конец-в-конец система выдержит меньше. Это ограничение
архитектуры MVP, а не измерения — см. запросы для проверки очереди в конце
файла.

## Пороги

Прогон падает сам, без чтения глазами.

`contention.js` содержит главную проверку:

```js
orders_created:      [`count<=${STOCK}`, `count>=${STOCK}`],
orders_out_of_stock: ['count>0'],
orders_unexpected:   ['count==0'],
```

Верхняя граница ловит **перепродажу**, нижняя — **потерю остатка** (часть
товара «испарилась», не превратившись в заказ). Требование ненулевых отказов
гарантирует, что гонка вообще случилась, а не попыток было меньше остатка.
Дополнительно `teardown` читает витрину и требует, чтобы остаток обнулился.

## Развёртка: где потолок и где узкое место

Один прогон отвечает «выдержал или нет». Чтобы найти предел и понять, во что
он упирается, нужна серия прогонов с растущим параметром:

```bash
./load/sweep.sh throughput   # потолок пропускной способности записи
./load/sweep.sh contention   # цена конкуренции при росте числа клиентов
./load/sweep.sh spread       # блокировка строки или что-то общее?
```

Скрипт гоняет k6 несколько раз, собирает `--summary-export` и сводит в таблицу
med / p95 / p99 / max. Столбец «исход» показывает, чем закончился каждый
прогон: пусто — всё сошлось, «пороги» — ожидаемое для развёртки нарушение
порога, «СБОЙ» — прогон не состоялся. При любом «СБОЙ» скрипт печатает хвост
лога k6 и возвращает ненулевой код: таблица с прочерками, выданная за
результат, — худшее, что может сделать инструмент, чья задача отличать провал
от победы.

Ниже — результаты прогона от 2026-08-27 на AMD Ryzen 7 4800H (16 потоков),
14 ГБ RAM, PostgreSQL 17.5, Go 1.26.7. Генератор нагрузки, сервис и база — на
одной машине.

**Оговорка к точности.** Каждая строка таблиц — **один прогон**, без
повторений и доверительных интервалов. Абсолютные значения содержат шум
соседних процессов; при `VU=200` на каждого клиента приходится всего 4–5
успешных заказов, и p99 там посчитан по 900 точкам. Выводы ниже опираются не
на отдельные числа, а на форму зависимости, которая между прогонами
воспроизводится.

### 1. Корректность держится при любой конкуренции

300 порций на одной строке, 900 попыток, растёт только число клиентов:

| VU  | продано | усп. med | усп. p95 | усп. p99 | отказ p95 | отказ p99 |
|-----|---------|----------|----------|----------|-----------|-----------|
| 1   | **300** | 2,58     | 4,72     | 5,07     | 3,22      | 3,55      |
| 5   | **300** | 7,21     | 12,89    | 16,82    | 2,72      | 3,37      |
| 10  | **300** | 11,45    | 31,34    | 48,09    | 4,00      | 7,76      |
| 25  | **300** | 33,97    | 124,65   | 162,19   | 6,36      | 32,47     |
| 50  | **300** | 80,31    | 155,73   | 218,16   | 31,60     | 92,31     |
| 100 | **300** | 150,63   | 246,55   | 309,50   | 108,81    | 124,94    |
| 200 | **300** | 345,65   | 364,59   | 553,41   | 209,83    | 215,20    |

Продано ровно 300 на каждом шаге — от одного клиента до двухсот. Инвариант не
зависит от степени конкуренции, и это главное, что доказывает таблица.

### 2. Задержка растёт линейно с числом клиентов

Начиная с 25 VU медиана успешного заказа делится на число клиентов почти в
константу: 1,36 → 1,61 → 1,51 → 1,73 мс на клиента. Это подпись **сериализации**:
каждый следующий клиент не получает свою долю параллелизма, а встаёт в очередь.

Отсюда прямо считается потолок продаж **одной позиции**: около 1,5 мс на заказ,
то есть **≈650 продаж в секунду с одной строки**, сколько клиентов ни добавляй.
Добавление клиентов сверх этого увеличивает только время ожидания.

**Неочевидное следствие: отказ не бесплатен.** Задержка отказа тоже растёт —
с 3,5 мс при одном клиенте до 215 мс при двухстах. Причина в том, что
`OUT_OF_STOCK` выясняется не заранее, а внутри того же `UPDATE`: чтобы узнать,
что остатка нет, транзакция обязана дождаться блокировки строки. «Быстрый
отказ» на деле стоит в той же очереди, что и успешная продажа.

### 3. Узкое место — именно блокировка строки

Тот же суммарный остаток, те же 100 клиентов, меняется только число строк,
между которыми дефицит разложен:

| строк | на строку | продано | усп. med | усп. p95 | усп. p99 |
|-------|-----------|---------|----------|----------|----------|
| 1     | 300       | 300     | 123,26   | 236,09   | 257,74   |
| 2     | 150       | 300     | 58,01    | 101,09   | 108,13   |
| 5     | 60        | 300     | 33,27    | 45,55    | 58,04    |
| 10    | 30        | 300     | 28,24    | 37,52    | 42,61    |
| 25    | 12        | 300     | 28,41    | 35,74    | 39,56    |
| 50    | 6         | 300     | 27,18    | 34,44    | 40,72    |

Задержка обратно пропорциональна числу строк: две строки — вдвое быстрее,
пять — вчетверо. Это исключает все общие объяснения (пул, CPU, диск, сеть):
нагрузка неизменна, меняется только степень конкуренции за конкретную строку.

Столбец «продано» при разносе — наблюдение, а не утверждение: позиция
выбирается случайно, и часть строк может остаться нераспроданной, поэтому
порог требует лишь `count<=STOCK` (отсутствие перепродажи). Полная распродажа
утверждается только при `SPREAD=1`, где весь остаток лежит на одной строке.

Кривая выходит на полку около десяти строк — дальше упирается уже не в
блокировку, а в общий предел системы при ста одновременных клиентах.

### 4. Потолок пропускной способности — 2400 запросов в секунду

Позиции с неограниченным остатком, конкуренции за строку нет, постоянная
интенсивность:

| цель, rps | факт, зак/с | med    | p95       | p99       | max    | недодано |
|-----------|-------------|--------|-----------|-----------|--------|----------|
| 200       | 199,95      | 3,96   | 5,08      | 5,68      | 23,66  | 0        |
| 400       | 399,79      | 3,01   | 5,04      | 5,66      | 25,30  | 0        |
| 800       | 799,72      | 2,47   | 4,07      | 6,27      | 17,67  | 0        |
| 1200      | 1199,37     | 2,79   | 4,29      | 11,45     | 33,27  | 0        |
| 1600      | 1599,05     | 3,01   | 4,75      | 17,43     | 43,68  | 0        |
| 2400      | 2398,55     | 3,59   | **51,52** | **89,31** | 131,78 | 0        |
| 3200      | **3128,15** | 565,70 | 750,14    | 783,48    | 815,56 | 0        |

Столбец «недодано» — `dropped_iterations`: сколько запросов k6 не смог выдать
в заданном темпе. Всюду ноль, то есть генератор успевал, и замеренная задержка
не занижена за счёт запросов, которые так и не ушли. На 3200 rps отставание
«факта» от «цели» вызвано не потерянными итерациями, а тем, что каждая длилась
дольше отведённого ей интервала.

Три режима читаются однозначно:

- **до 1600 rps** — рабочая зона: задержка ровная, p99 до 17 мс;
- **2400 rps** — колено: медиана ещё 3,6 мс, но p95 подскакивает в десять раз.
  Очередь появилась, среднее её пока не показывает — видно только по хвосту;
- **3200 rps** — обвал: медиана 566 мс, и сервис перестаёт догонять цель.

Именно ради этой границы в таблице есть p99. По медиане переход с 1600 на 2400
почти незаметен (2,79 → 3,59 мс), а по p99 — рост в пятнадцать раз.

### 5. Пул соединений имеет оптимум, а не «чем больше, тем лучше»

Одна и та же нагрузка 2400 rps при разном `DB_MAX_CONNS`:

| пул | факт, зак/с | med       | p95       | p99        |
|-----|-------------|-----------|-----------|------------|
| 5   | **1720,10** | 2048,23   | 2967,72   | 2978,75    |
| 10  | 2395,89     | 4,94      | 94,42     | **106,91** |
| 20  | 2396,88     | **3,90**  | **69,63** | 112,40     |
| 50  | 2397,00     | 4,10      | 88,11     | 187,03     |
| 100 | 2386,74     | 4,61      | 259,00    | **355,74** |

Результат контринтуитивный и стоит отдельного внимания.

Пул из пяти соединений мал очевидно: пропускная способность падает до 1720/с,
задержка — две секунды. А вот дальше **пропускная способность не растёт вообще**
(2396 против 2397), зато хвост уверенно portится: p99 идёт 107 → 112 → 187 → 356.

Объяснение в том, что пул работает как контроль допуска. Он не ускоряет базу, а
ограничивает число одновременных транзакций. Увеличивая пул, мы не добавляем
мощности — мы переносим очередь из приложения, где ожидание дёшево, внутрь
PostgreSQL, где сто конкурирующих бэкендов дерутся за буферы, блокировки и
процессор. Работа размазывается тоньше, и заканчивают все позже.

Практический вывод: `DB_MAX_CONNS=10` по умолчанию — не заниженное значение, а
рабочая точка. «Поднять пул, когда тормозит» — типовая ошибка, и эта таблица
показывает её цену.

### 6. Стена — процессор PostgreSQL

Загрузка под нагрузкой 2400 rps на 16 потоках:

```
postgres ....... 571 %   (≈5,7 ядра)
api ............ 277 %   (≈2,8 ядра)
k6 (генератор) . 219 %   (≈2,2 ядра)
──────────────────────
итого .......... ≈10,7 из 16 ядер
```

База съедает вдвое больше приложения — потолок упирается в неё, а не в Go-код и
не в пул. Отдельно стоит заметить, что сам генератор нагрузки забирает пятую
часть машины: измеренный потолок **занижает** реальную способность сервиса,
потому что k6 отнимает ресурсы у того, что измеряет.

## Слабые точки: итог

| # | Что | Насколько | Что с этим делать |
|---|-----|-----------|-------------------|
| 1 | Блокировка строки популярной позиции | ≈650 продаж/с с одной строки, дальше растёт только очередь | Шардировать остаток на N строк-«корзин» либо вынести резервы в отдельную таблицу с TTL |
| 2 | Отказ по остатку ждёт ту же блокировку | 215 мс p99 при 200 клиентах вместо 3,5 мс | Проверять остаток до транзакции — но тогда появляется гонка; либо кэш «позиция кончилась» с коротким TTL |
| 3 | Пул соединений сверх ~20 портит хвост | p99 в 3,3 раза хуже при пуле 100 против 10 | Не трогать; при росте — пулер (PgBouncer) в режиме transaction, а не раздувание пула приложения |
| 4 | CPU PostgreSQL | стена на ≈2400 rps | Реплики для чтения (витрина), шардирование по `restaurant_id` для записи |

Первая точка не дефект, а осознанный размен, описанный в
[ADR-0001](../docs/adr/0001_postgresql_as_single_source_of_truth.md): атомарность
куплена ценой сериализации. Замер даёт этому размену цифру — до нескольких сотен
продаж в секунду с одной позиции, чего для MVP заведомо достаточно.

Вторая обнаружилась именно замером и в ADR не описана — это честная находка.

### Как читать эти числа

Это **не производительность в проде**. Генератор, сервис и база делят одну
машину, сетевой задержки нет, а k6 забирает пятую часть процессора. Реальные
значения будут другими.

Ценность в другом:

- **База для сравнения.** Вырастет p99 оформления с 5 мс до 50 — видно сразу.
- **Форма кривой.** Линейный рост задержки от числа клиентов на одной строке и
  полка при разносе — это свойства архитектуры, а не железа. На другой машине
  сдвинутся абсолютные значения, но не форма.
- **Порядок величины.** Оформление за единицы миллисекунд означает, что в
  горячем пути нет случайного N+1 или забытого индекса.

Что осталось непроверенным: длинная дистанция (часы), рост таблиц `orders` и
`outbox_events`, несколько экземпляров `api` одновременно, поведение при
недоступной базе.

## Куда смотреть после прогона

Очередь исходящих событий — не растёт ли она быстрее, чем разгребается:

```sql
SELECT count(*) FILTER (WHERE sent_at IS NULL AND dead_at IS NULL) AS ожидают,
       count(*) FILTER (WHERE sent_at IS NOT NULL)                 AS доставлены,
       count(*) FILTER (WHERE dead_at IS NOT NULL)                 AS сняты,
       max(attempts)                                               AS макс_попыток
FROM outbox_events;
```

Конфликты оптимистичной блокировки видны в логах по коду `STATE_CONFLICT`:

```bash
docker compose logs api | grep -c STATE_CONFLICT
```
